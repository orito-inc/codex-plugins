# conformist

「新しく考える」より「既存に合わせる」を優先する。設計やコードを作る前に、本リポジトリの類似実装を探し、現在の要件を満たす既存パターンを踏襲する。

## 参考実装の探索順序

1. 同一機能・同一ドメインの既存実装
2. 同一ディレクトリ・同一モジュールの類似実装
3. リポジトリ内の同種機能
4. AGENTS.md / CLAUDE.md / README / coding conventionsなどの明示ルール
5. フレームワークや一般的なベストプラクティス

これは参考実装を探す優先順位であり、指示の優先順位ではない。適用される明示ルールは作業開始時に確認し、すべての候補に対する制約として守る。既存コードを根拠に規約違反を追加しない。

## 適用

- シンボル検索や `rg` で対象を絞り、候補の実装・呼び出し元・関連テストを必要な範囲で読む。名前が似ているだけで選ばず、目的・入出力・責務が対応するか確認する。
- 構造・責務分割・命名・処理フロー・使用ライブラリ・helper・component・validation・error handling・logging・test patternを照合する。今回の変更に関係するものだけを踏襲または再利用する。
- 既存部品が目的に合い、依存規約上も利用可能なら、独自実装より再利用を優先する。直接再利用できない場合は既存の形を踏襲し、要件固有の差分だけを加える。再利用のためだけのwrapper・共通基盤・dependencyは追加しない。
- 複数のパターンがある場合は探索順位と適用範囲で選ぶ。孤立した例外や廃止予定の実装を標準と断定しない。明示された移行方針があれば従い、根拠がなければ好みで新しいパターンへ統一しない。
- 一般論として綺麗・新しい・抽象的、将来拡張できそうという理由だけで新しいパターンを導入しない。既存に合わせるために、今回必要のない機能や構造までコピーしない。

## 踏襲できない場合

既存パターンから外れる前に「どの現在要件が、どの既存パターンでは満たせないか」を具体的に確かめる。

- 明らかなbug・security問題・現在の明示要件との矛盾は引き継がない。問題のない部分は踏襲し、必要な差分だけを設ける。無関係な既存コードの全面改修へ広げない。
- 文書と実装のどちらを正とするか不明な場合は確認し、実装に合わせて仕様を勝手に変更しない。根拠が揃っている通常の実装判断では、追加の承認工程を作らない。
- 適切な前例が見つからなければ、探した範囲と不足点を短く示す。明示ルール、採用中のフレームワーク・ライブラリの標準機能の順に頼り、独自部分を最小限にする。

## レビューと検証

レビューでは、今回の変更だけが既存パターンから外れる箇所と、踏襲・再利用によって独自実装を削除できる箇所を指摘する。各指摘に以下を含める。

- **対象:** 変更箇所のファイル・シンボル・文書の節。
- **根拠:** 参考実装の場所または適用ルールと、今回に適用できる理由。
- **最小修正案:** 何を既存に合わせ、何を再利用し、どの独自実装を削除するか。

好みの差を規約違反として扱わない。必要性のある逸脱は理由を示し、踏襲不能な不具合とは区別する。レビュー依頼では指摘を返し、編集依頼では対象範囲に反映する。

変更後は追加・変更したimport/useのレイヤー依存と、既存に合わせた振る舞いを確認する。リポジトリ規約に従う最小限のtest / lint / typecheck / format等を実行し、変更ファイル・踏襲元・必要な逸脱・実行した検証と未確認事項を簡潔に報告する。
